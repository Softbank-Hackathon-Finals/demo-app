# T22 장시간 로컬 부하 검증 — 실패 기록 보존

## 첫 시험

앱·PostgreSQL·OTel Collector·Prometheus·T36 수신기를 실제로 실행했다. 환경별 30분,
초당 쓰기 50/읽기 150의 순차 시험이다. 두 앱은 같은 로컬 DB를 사용하며 AWS API는
moto다. 팀 EKS/RKE2, 실제 Edge·Tailscale 또는 데이터 이전 자격 시험이 아니다.

- 출발지: 쓰기 90,000건 중 확인 89,580건, 실패 420건(미저장 400/저장됐으나 미확인 20).
  확인 응답 후 유실 0·중복 0이지만 전체 성공은 아니다. HTTP 오류율 6.6362%, 전체 p95 15.09초.
  관측 창 180개 중 전달 실패 82개, 귀속 불가 timeout 22,918건. **FAIL**.
- 목적지: 쓰기 90,000건 전수 대조, 실패·유실·중복 0, HTTP 오류 0, 전체 p95 7.464ms.
  같은 부하에서 관측 창 180개 전달. 이 경로의 성공이 출발지 실패를 상쇄하지 않는다.
- 별도 1Hz 표시 조회는 실패 0이었지만 전체 업무 부하의 성공 근거가 아니다.
- 실제 WS 1012·동일 시험 URL 재연결·멱등 재시도 1행·Collector 중단 시 UNOBSERVABLE은 통과.

출발지 로그에 PoolTimeout이 있다. 같은 호스트에서 다른 컨테이너 자격 시험이 겹쳤으므로
자원 경합 가능성은 있지만 원인을 확정하지 않았다. 쓰기 순서 보호용 advisory lock을
제거하거나 성공 기준을 완화하지 않았다. 최초 결과는 변경하지 않고 `first-summary.json`으로
공개 요약한다. 원문은 테스트용 메시지/로컬 주소 등을 포함해 비공개로 보존하고 내용 해시를 남긴다.

## 판정 보완

마지막 Prometheus 창의 오류 0과 최종 DB 대조 PASS만으로 장시간 실행 전체를 통과시키지 않는다.
하네스는 전체 HTTP·계약 오류, 관측 창 전달/보존/누락, 부하 생성기 경고를 별도 검사한다.
이는 로컬 시험 자격 검사이며 T36 운영 임계치나 실제 Edge 관측 판정을 대체하지 않는다.

같은 앱 소스를 고정한 별도 두 번째 시험에서 다른 무거운 컨테이너 시험을 피하고
호스트/컨테이너 자원 사용량을 기록한다. 첫 실패 기록을 지우지 않고 결과를 별도로 비교한다.
